# Skill Safety Boundary

The platform is **not safety-certified.** This document records the
strict separation between the Phase 15A robotics skill authoring
workbench and the runtime safety authority.

## 1. The architecture in one diagram

```
   developer request
            │
            ▼
   skill authoring workbench
            │
            ▼
   code candidate
            │
            ▼
   template validator
            │
            ▼
   safety review + audit
            │
            ▼
   copyable snippet (read-only artefact)
            │
            ▼
   developer runs the snippet (off the rover, on a workstation)
            │
            ▼
   snippet publishes /cmd_vel_requested
            │
            ▼
   Safety supervisor  ────────────  authoritative
            │
            ▼
   Motion arbitration
            │
            ▼
   Authorized command  ───────────  /cmd_vel_authorized
```

The workbench never publishes anything. The workbench cannot grant
actuator authority. The workbench's output is text; the runtime
safety supervisor remains the only path to motion.

## 2. What the workbench CAN do

* parse a deterministic set of developer-request shapes;
* select a template from a closed catalog;
* render copyable code with bounded parameters;
* attach a safety review and a code-card metadata payload;
* write an audit bundle that records exactly what happened.

## 3. What the workbench MUST NOT do

| Forbidden                                              | Enforcement                                                |
|--------------------------------------------------------|------------------------------------------------------------|
| publish to `/cmd_vel` or `/cmd_vel_authorized`         | no template emits these; validator rejects in executable code |
| toggle the safety supervisor                           | parser rejects "disable safety" / "ignore safety"          |
| override e-stop                                        | parser rejects "override estop"                            |
| produce unbounded motion / speed                       | parser rejects; templates use bounded loops only           |
| disable lidar / sensors                                | parser rejects "disable lidar"                             |
| run shell, run code, run network commands              | parser rejects; validator rejects forbidden imports        |
| call a remote LLM API                                  | no LLM SDK imports in the package                          |
| execute generated code                                 | CLI only writes files; no `subprocess` / `eval`            |
| publish anything to ROS                                | no `rclpy` import in the package itself                    |
| produce hardware-driver code                           | no driver template exists                                  |

## 4. Why these boundaries

Robotics developer tooling that sits next to a safety supervisor
must treat every generated snippet as untrusted code. The
workbench therefore:

1. only emits code that uses *requested-motion* interfaces;
2. only emits bounded loops with timeout / count / watchdog
   guards;
3. always appends a final zero `Twist` for motion templates;
4. mentions the safety supervisor in a comment header so a reader
   cannot mistake the snippet for an authorising command;
5. re-validates the rendered text before writing the audit bundle.

## 5. Audit trail

Every generation produces a read-only audit bundle. The bundle
records the request, the parser candidate, the rendered code, the
safety review, the diagnostics, and the verbatim disclaimer. The
bundle is reproducible: with the same `--generated-at`, the same
request yields byte-identical output.

## 6. Honesty rules

* No artefact in `skill-library/` represents a runtime mission.
* No artefact in `skill-library/` claims safety certification.
* No artefact in `skill-library/` is generated by a real LLM call.
* A snippet that compiles cleanly is *eligible* for review by a
  developer; it is not authorised to run on the robot.

A future external local-LLM provider (see
`docs/FUTURE_LOCAL_LLM_SKILL_PROVIDER.md`) must keep the
deterministic catalog as the authority and must pass every
proposed snippet through this validator.
