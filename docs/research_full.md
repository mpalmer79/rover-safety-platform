# Autonomous Safety Validation Rover Platform Research Brief

## Executive Summary

The strongest direction for this portfolio project is a simulation-first autonomous rover built on entity["software","ROS 2","robotics middleware"] Jazzy on Ubuntu 24.04, with entity["software","Gazebo","robotics simulator"] Harmonic as the primary simulator, a lifecycle-managed node graph, an explicit safety supervisor, and a full observability pipeline built around logs, bags, traces, and replay. That recommendation is not based on popularity. It is based on support horizon, ecosystem fit, and the fact that Jazzy is the current LTS release through May 2029, its target-platform matrix explicitly pairs Ubuntu Noble with Gazebo Harmonic, ROS 2 uses DDS-backed middleware with configurable QoS, and Gazebo remains the first open-source choice for 3D physics simulation of ROS-based robots. citeturn28view4turn28view3turn38search1turn29view1turn29view2

The MVP should be narrow and rigorous: a differential-drive rover in a known or semi-structured environment that ingests 2D LiDAR, wheel encoders, IMU, and a contact or bumper channel; fuses state; scores confidence and disagreement; enforces degraded modes; arbitrates the final motion command; and produces replayable incident timelines. That scope aligns with what entity["software","Navigation2","ROS 2 navigation stack"] already provides for lifecycle-managed navigation, behavior-tree orchestration, keepout and speed filters, and velocity smoothing, while `robot_localization` provides EKF and UKF state-estimation nodes for the encoder and IMU fusion pattern that mobile robots commonly use. citeturn25view5turn21view1turn40search3turn40search1turn40search4turn23view2

What should be deferred is just as important as what should be included. Full SLAM, camera-first perception, GNSS-dependent autonomy, and entity["software","Isaac Sim","robotics simulator"] should all come later. Odometry drift and IMU bias are real, and the rover should explicitly model them, but early camera and GNSS work add calibration, synchronization, and environment-variability costs before the safety architecture is stable. Isaac Sim has valid ROS 2 integration, but its current documentation still labels 6.0 as an Early Developer Release, while recent system-requirements guidance starts at workstation-class GPU and memory targets that are misaligned with a practical single-engineer MVP. citeturn23view8turn23view6turn23view7turn22view5turn22view6turn22view4

## Recommended Technical Direction

The recommended technical direction is to use ROS 2 as middleware, not as the architecture itself. In professional systems, topics carry continuous sensor and state streams, services are reserved for short-lived RPC-style operations, and actions are used for long-running, preemptable behaviors like waypoint execution and recovery. DDS-backed QoS exists specifically so communication semantics can be tuned for reliability, lossy networks, and deadline-sensitive systems; executor choice, callback groups, and wait sets are the mechanisms that determine whether your pipeline is merely concurrent or genuinely predictable. citeturn39view0turn21view3turn25view7turn25view8turn36search1

The recommended architecture style is a layered, event-driven autonomy stack with hard subsystem boundaries. Sensor adapters publish raw standardized messages. State estimation produces the canonical pose and velocity estimate. A confidence and disagreement evaluator consumes both raw and fused state to produce health and trust signals. A mission layer, ideally using entity["software","BehaviorTree.CPP","C++ behavior tree library"], handles waypointing and recovery. A separate safety supervisor owns degraded-mode transitions and final command arbitration. The motor gateway, whether simulated or physical, is the only component allowed to write actuator commands. That decomposition mirrors how Nav2 itself separates behavior trees, planning, control, costmaps, and lifecycle bringup, while the ROS 2 composition model lets deployment remain flexible: same code, different process layout. citeturn25view0turn25view2turn25view3turn25view4turn25view6

A sensible repository shape is a multi-package colcon workspace, not a monolith:

```text
rover_ws/
  src/
    rover_msgs/
    rover_description/
    rover_bringup/
    rover_sim_gazebo/
    rover_hw_gateway/
    rover_sensor_adapters/
    rover_state_estimation/
    rover_world_model/
    rover_safety_supervisor/
    rover_mission_bt/
    rover_observability/
    rover_fault_injection/
    rover_dashboard_gateway/
    rover_tests/
    rover_docs/
```

That layout matches how ROS 2 workspaces are structured around `src`, `build`, `install`, and `log`, and it keeps message contracts, launch files, parameters, libraries, tests, and documentation separable. In practical terms, that matters because `package.xml`, `CMakeLists.txt`, node parameters, and launch-time composition choices become part of the operational contract instead of accidental implementation detail. citeturn37view1turn37view0turn37view3

The primary tradeoff is performance versus fault isolation. Composition can reduce overhead and improve intra-process communication, but separate processes are easier to debug and isolate when a node crashes. For the MVP, the right compromise is to keep the safety supervisor, recorder, and hardware gateway in separate processes, then consider composing only the fast-path estimation and validation stages after profiling. Common failure modes at this layer are callback starvation, hidden shared-state bugs, deadlocks in multi-threaded executors, and nondeterministic callback ordering. If the core decision loop needs stronger sequencing guarantees, a wait-set-driven path is better than ad hoc thread pools because ROS 2 explicitly documents wait sets as a way to implement deterministic, user-defined processing sequences. citeturn25view6turn25view7turn25view8turn36search1turn36search8

Mission orchestration and safety logic should not be modeled the same way. A behavior tree is the right abstraction for navigation goals, recovery, and non-blocking reactive behavior because BehaviorTree.CPP is explicitly built for asynchronous actions, modular runtime-loaded nodes, and robotics use cases. Safety behavior should remain a finite, explicit, auditable state machine. That split is one of the clearest markers that the project is architectural rather than hobby-grade. citeturn25view0turn25view1turn25view2

## Architecture and Safety Model

Safety-critical autonomy matters here because the project’s value is in controlled behavior under uncertainty, not in nominal motion. The right conceptual model borrows from the ODD and fallback framing used by the entity["organization","National Highway Traffic Safety Administration","United States transportation safety agency"] and from industrial robot safeguarding guidance maintained by the entity["organization","Occupational Safety and Health Administration","United States workplace safety regulator"] and the entity["organization","Association for Advancing Automation","robotics industry association"]. In other words, the rover should have explicit operating boundaries, documented methods for detecting degraded operation or ODD exit, and a minimal-risk behavior that is defined before code is written. citeturn24view0turn24view1turn24view2turn24view3turn24view6

The recommended safety state machine is: Boot, Inactive, Active-Normal, Active-Restricted, Active-Degraded, Safe-Stop, E-Stop-Latched, and Recovery. `Active-Restricted` is for situations where the rover still has enough trusted state to move, but only at reduced speed or in a reduced zone set. `Active-Degraded` is for one noncritical sensor loss with preserved minimum sensing, such as continuing on LiDAR and odometry after losing an auxiliary proximity channel. `Safe-Stop` is the fallback minimal-risk condition. `E-Stop-Latched` is a human or hard fault state that requires an explicit operator reset. This fits well with ROS 2 lifecycle nodes because lifecycle management already gives deterministic startup, activation, deactivation, cleanup, and shutdown semantics, and Nav2’s lifecycle manager already transitions ordered nodes one by one and tears the stack down if a bonded node becomes non-responsive. citeturn21view2turn21view1turn25view5

Professionals use freshness monitoring at more than one layer, and this project should do the same. At the middleware layer, DDS deadline QoS can raise alarms when an expected stream stops showing up at the promised rate. At the software layer, heartbeat and command timeout rules should inhibit motion if the autonomy stack stops producing fresh outputs. At the embedded layer, a watchdog timer should reset or disable the low-level controller if it stops receiving the expected kick or heartbeat. The MVP should include exactly these controls: one freshness rule for every critical stream, one timeout-to-zero rule for commanded velocity, and one hardware path that can remove motor power. Full fail-operational redundancy and true majority voting should be deferred, because for a single-engineer mobile platform the higher-value pattern is disagreement detection with graceful degradation, not pretending to have aircraft-style redundancy without the budget or verification burden to support it. citeturn24view5turn17search3turn40search4turn24view2

The event model should make safety explainable. Every transition into Restricted, Degraded, Safe-Stop, or E-Stop-Latched should emit a discrete event with cause code, triggering stream, last-seen timestamp, confidence values, final command, and recovery path. Common failure modes worth modeling from the start are stale LiDAR, wheel-slip divergence between encoder odometry and inertial motion, bridge disconnects, command timeout, and recovery failure after repeated action preemption. These are not abstract ideas. They are exactly the kinds of observable transitions a principled autonomy portfolio should make inspectable and replayable. citeturn24view1turn39view0turn21view7turn21view6

## Simulation and Sensor Strategy

The recommended simulator is Gazebo. The reasons are concrete. Gazebo is the ROS ecosystem’s first open-source choice for 3D physics simulation of ROS-based robots; Gazebo Sim exposes high-fidelity physics, rendering, sensors, plugins, transport, and command-line introspection; and the ROS 2 integration story is mature through `ros_gz_bridge`, including launch-time YAML bridge configuration and composition support. Most importantly, Jazzy’s target-platform matrix explicitly pairs Ubuntu 24.04 with Gazebo Harmonic, which matters more than chasing the theoretically best simulator because it reduces integration risk and keeps the project anchored in a supported ROS-native path. citeturn29view1turn29view2turn21view11turn28view3

entity["software","Webots","robotics simulator"] is the best secondary choice when scenario reset control and desktop convenience matter more than ROS-native depth. Its official site positions it as an open-source, multi-platform professional simulator used in industry, education, and research, and the ROS 2 tutorials expose a Ros2Supervisor node plus reset-handler patterns that are genuinely valuable for repeatable scenario testing. entity["software","PyBullet","Python physics simulator"] is very good for controller prototyping because its official quickstart centers on direct Python control, deterministic `stepSimulation()`, headless `DIRECT` mode, URDF loading, and remote networking options, but that same design emphasis makes it a poor primary simulator for a ROS-first portfolio. Isaac Sim is powerful and ROS 2 capable, but its current docs still flag 6.0 as an Early Developer Release, while current requirements assume a much heavier workstation profile. citeturn22view0turn22view1turn22view2turn32view0turn22view5turn22view6turn22view4

The MVP simulation strategy should be intentionally constrained. Start with a differential-drive rover, a known map or bounded route, and a small suite of injected hazards. Use standard ROS message boundaries everywhere so only the adapter package changes when moving from simulation to real hardware. In Gazebo, bridge `/scan`, `/tf`, odometry, clock, and command topics through a YAML `ros_gz_bridge` configuration rather than hand-coded glue, and inject faults at the adapter layer so the rest of the autonomy stack cannot tell whether the fault came from simulated physics, a delayed bridge, or a faulty hardware driver. That is the correct abstraction layer for a simulation-first architecture. citeturn21view11turn28view5turn21view9turn29view0

The recommended MVP sensor stack is 2D LiDAR, wheel encoders, IMU, and a contact or bumper channel. Why this matters is simple: Nav2’s obstacle layer is already built around 2D raycasting for 2D lidars, depth, and similar sensors, and the standard odometry setup documentation explicitly calls out wheel encoders plus IMU as the usual sensor sources fused through `robot_localization` EKF or UKF nodes. Professionals use this stack because it gives you a clean separation between obstacle awareness, short-term localization, and last-resort collision detection without forcing a jump into vision compute on day one. citeturn23view3turn23view2turn23view0

The common failure modes are also well understood. Wheel odometry accumulates error through slip, skid, and numerical integration drift. IMUs drift because bias and in-run bias stability put a floor under how well the bias can be estimated. Low-cost ultrasonic sensing is finicky because tilted, curved, soft, or partially deflective targets reduce the echo response, and ambient temperature, humidity, and debris change range performance. That is why ultrasonic should be a near-field secondary cross-check, not the primary planner input. For fault injection, this is excellent news: every one of those failure modes can be simulated or emulated and then validated against the safety state machine. citeturn23view8turn23view6turn23view7turn23view5

The initial sensors to avoid are camera-first perception and GNSS-first navigation. GPS integration in `robot_localization` immediately introduces `navsat_transform_node` and another frame-alignment problem, while urban and multipath-heavy conditions directly affect GNSS performance. Camera pipelines are not wrong, but they push the project toward heavier compute and more calibration before the decision, safety, and replay pathways are trustworthy. For this particular portfolio objective, those are phase-later capabilities, not foundational ones. citeturn23view0turn8search2turn8search0turn8search4turn22view5turn28view2

## Compute, Hardware, and Telemetry

The recommended physical MVP hardware is a companion-computer plus microcontroller split. The cleanest first hardware step is entity["product","Raspberry Pi 5","single-board computer"] as the companion computer and entity["software","micro-ROS","ROS 2 for microcontrollers"] or an equally narrow MCU-side protocol for the safety and actuator island. Raspberry Pi 5 offers up to 16 GB RAM, Ethernet, USB 3, a PCIe connector, camera-display ports, and a higher-power operating mode; micro-ROS exists specifically to put ROS 2 onto microcontrollers, and the agent supports serial, UDP, and TCP transport. That architecture is realistic, scalable, and professionally legible because it avoids pretending a Linux SBC is a hard real-time motor controller. citeturn22view8turn22view7turn22view10turn22view11

The hardware upgrade path should be explicit. Move to entity["product","Jetson Orin Nano Super Developer Kit","edge AI developer kit"] only when the project has a real need for onboard camera or learned perception workloads. Current official materials position the Super Developer Kit at $249 and the Orin Nano family as an edge-AI platform with 5 W to 15 W power options and up to 40 TOPS for the module family, while also reminding users that developer kits are for software development and prototyping. The principal-level signal here is not owning the most impressive board. It is proving that hardware escalation happened for a traceable systems reason. citeturn28view2turn22view9turn28view0turn28view1

Observability should be treated as a first-class subsystem. ROS 2 already provides three foundational layers: logging to console, disk, and `/rosout`; bag recording and replay; and low-level tracepoints via `ros2_tracing`. In current rosbag2, MCAP is the default storage format and the MCAP plugin is maintained directly in the rosbag2 repository. For live introspection, use entity["software","Foxglove Bridge","robotics visualization bridge"] together with entity["software","Foxglove","robotics observability tool"] because the official docs emphasize low overhead, support for ROS 2 schemas, parameters, graph introspection, and both desktop and browser workflows. citeturn21view6turn21view7turn21view4turn27view0turn27view1turn27view2turn27view3turn21view8

The telemetry architecture should separate streams by purpose. Raw topic archives belong in rosbag2 or DDS-level recording. Discrete incident events belong in an append-only event stream with compact indexed metadata. Health metrics belong in time-series telemetry. The event schema should always include timestamp, run ID, scenario ID, node, active lifecycle and safety states, source freshness, per-sensor confidence, disagreement score, requested motion, final commanded motion, and reason code. Dashboards should show state transitions, topic freshness, action status, stop latency, and replay timelines. Later, if DDS-layer record and replay becomes valuable, `DDS Record & Replay` is the right phase-later tool because it stores MCAP with original publication timestamps and supports exact playback with topic filtering and rate control. citeturn27view4turn21view7turn21view6turn27view3

## Phase Roadmap

**Phase 0** should produce architecture contracts, not robot motion. Objectives are the ODD definition, subsystem contracts, package layout, safety state machine, event schema, and an ADR set covering ROS 2 Jazzy, Gazebo Harmonic, and the initial sensor stack. The main risk is skipping this because “it is only a portfolio project,” which is exactly how hobby projects stay hobby projects. Dependencies are minimal. Complexity is moderate because most of the work is thinking and documentation. Deliverables are diagrams and contracts. Portfolio value is very high because this phase shows systems-architect behavior. citeturn28view4turn28view3turn24view0turn24view1turn37view1

**Phase 1** should bring up the simulation-only rover. Objectives are Gazebo rover description, bridge configuration, basic diff-drive motion, sensor topics, and reproducible launch. The main risk is overbuilding the world instead of stabilizing interfaces. Dependencies are Phase 0 contracts. Complexity is moderate. Deliverables are the simulator package, launch files, and a short nominal run. Portfolio value comes from proving that the architecture is executable. citeturn21view11turn29view2turn21view10

**Phase 2** should implement the deterministic autonomy core. Objectives are state estimation, action-based waypoint execution, mission behavior tree, and decision-loop sequencing. The main risk is hidden nondeterminism from careless executor and callback-group choices. Dependencies are stable message contracts and simulator bringup. Complexity is moderate to high. Deliverables are filtered odometry, action goals, and repeatable waypoint completion under replay. Portfolio value comes from demonstrating disciplined autonomy structure instead of ad hoc callbacks. citeturn23view2turn39view0turn25view0turn25view8turn36search1

**Phase 3** should add safety supervision and degraded modes. Objectives are deadline and freshness checks, software heartbeats, confidence scoring, disagreement detection, restricted-speed behavior, safe-stop behavior, and E-stop latching. The main risk is building state proliferation without a crisp transition model. Dependencies are a working decision loop and telemetry hooks. Complexity is high because this is where the architecture becomes interesting. Deliverables are scenario-driven transitions for stale sensors, bridge loss, and odometry divergence. Portfolio value is extremely high because this is the phase that makes the project look production-minded. citeturn24view1turn24view5turn17search3turn40search4

**Phase 4** should make failures observable and replayable. Objectives are rosbag2 recording as a default runtime behavior, trace capture during critical tests, event indexing, and Foxglove dashboards for transition timelines and command arbitration. The main risk is creating telemetry that is visually attractive but operationally useless. Dependencies are well-defined events and working degraded modes. Complexity is moderate. Deliverables are live dashboards, replay workflows, and at least one incident reconstruction doc tied to a bag file. Portfolio value is high because it proves incident forensics capability. citeturn21view7turn21view4turn27view0turn27view3turn27view4

**Phase 5** should introduce hardware on the bench, not in the field. Objectives are the companion computer and MCU split, encoder and motor integration, watchdog validation, and command-timeout stop on real actuators. The main risk is discovering too late that the software stack assumed simulation behavior that hardware does not provide. Dependencies are a stable simulator-side hardware abstraction. Complexity is high because electrical and timing realities finally show up. Deliverables are bench videos, stop-latency measurements, and a sim-versus-hardware parity report. Portfolio value comes from demonstrating system transfer and restraint. citeturn22view8turn22view10turn22view11turn17search3

**Phase 6** should add optional perception and polish only if the architectural base is already credible. Objectives might include a camera pipeline, a Jetson migration, larger scenario libraries, and possibly Isaac Sim for perception-heavy experiments. The main risk is mistaking optional sophistication for core value. Dependencies are successful hardware-safe-stop replay and mature observability. Complexity is high and easy to underestimate. Deliverables are one clearly justified advanced capability plus documentation that explains why it belongs. Portfolio value is positive only if the addition preserves the project’s deterministic and explainable character. citeturn22view5turn22view6turn28view2

## Principal-Level Portfolio Signal

What separates this from hobby robotics is not the chassis, the simulator, or the presence of AI. It is the evidence trail. A senior reviewer will notice whether the project has an explicit ODD, lifecycle-managed bringup, parameterized subsystem boundaries, freshness-driven command inhibition, replayable incident data, and a clear explanation of what was deliberately deferred. They will also notice whether the execution model was treated seriously, because ROS 2 executors, callback groups, wait sets, and tracing directly influence whether replay and debugging are meaningful or merely approximate. citeturn24view0turn24view1turn25view5turn37view3turn25view8turn25view7turn36search1turn21view4

The documentation set should therefore be architecture-heavy and traceability-heavy: a system context diagram; runtime node, topic, service, and action graph; safety state machine; deployment diagram for sim and hardware; interface contracts for every package; ADRs; ODD and guardrail documentation; a risk register or FMEA-lite; the event-schema spec; and incident postmortem templates that point to exact bag files and traces. The most important tradeoffs should be documented explicitly, including why the project chose Jazzy over a newer non-LTS stack, Gazebo over alternative simulators, encoder-plus-IMU-plus-LiDAR over camera-first autonomy, and companion-computer-plus-MCU over single-board-only control. citeturn28view4turn28view3turn29view1turn23view2turn22view10turn37view1

The highest-value demo is not a clean lap. It is a controlled incident sequence. The ideal portfolio demo is a nominal run, followed by an injected stale LiDAR topic that transitions the rover into Restricted mode, followed by a simulated odometry divergence that triggers Safe-Stop, followed by a rosbag replay in Gazebo and a Foxglove timeline showing exactly why the state changed and what final command was sent. That kind of demo compresses resilience engineering, observability, explainability, and deterministic recovery behavior into a single artifact. citeturn24view1turn21view7turn21view11turn27view3

## Key Risks and Immediate Next Steps

The main risks are architectural, not mechanical. The project will fail as a principal-level signal if it becomes a generic Nav2 demo, if the motor loop runs directly on a non-real-time Linux SBC, if ultrasonic is treated as a primary planner sensor despite well-documented angle and material limitations, if camera AI is added before bag-based replay exists, or if the simulator choice outruns the workstation and destabilizes the development loop. All of those errors have the same root cause: complexity arriving before observability and control boundaries. citeturn21view5turn23view5turn22view4turn22view6turn29view0

The immediate next steps are straightforward:

1. Freeze the base stack as ROS 2 Jazzy on Ubuntu 24.04 with Gazebo Harmonic, and explicitly refuse scope creep into newer or heavier platforms until the core architecture works. citeturn28view4turn28view3
2. Write a one-page ODD and degraded-mode contract, including the exact conditions for Restricted mode, Safe-Stop, and E-Stop-Latched. citeturn24view0turn24view1turn24view6
3. Create the workspace skeleton and package boundaries before writing autonomy logic. Prioritize `rover_state_estimation`, `rover_safety_supervisor`, `rover_mission_bt`, and `rover_observability`. citeturn37view1turn37view0turn37view3
4. Bring up the Gazebo rover with LiDAR, encoder, IMU, contact sensing, and default bag recording. Add Foxglove and event emission at the same time, not later. citeturn21view10turn21view11turn23view2turn27view0turn27view3
5. Implement fault injection before hardware purchase. The first three tests should be stale scan, wheel-slip or odometry divergence, and command timeout to zero. citeturn24view5turn23view8turn40search4
6. Only after replayable Safe-Stop behavior works in simulation should the project move to entity["product","Raspberry Pi 5","single-board computer"] plus MCU hardware. Upgrade to Jetson only when a camera-driven capability is justified by a written requirement. citeturn22view8turn22view10turn28view2
