# LLM Safety Boundary

The platform is **not safety-certified.** This document records the
strict separation between the Phase 14B mission proposal layer
(LLM-shaped, but offline and mock-only) and the runtime safety
authority.

## 1. The architecture in one diagram

```
   Human language / LLM proposal
                 │
                 ▼
     Mission compiler  ────────────  Phase 14A
                 │
                 ▼
     Mission validator
                 │
                 ▼
     Mission runtime request
                 │
                 ▼
     Safety supervisor  ────────────  authoritative
                 │
                 ▼
     Motion arbitration
                 │
                 ▼
     Authorized command  ───────────  /cmd_vel_authorized
```

Only the safety supervisor and motion arbitration may authorize
movement. No node in the proposal layer or the mission compiler may
publish to `/cmd_vel` or `/cmd_vel_authorized`. This is asserted by
`backend/tests/test_mission_proposal.py` and by the architecture
tests already in place for Phase 14A.

## 2. What the proposal layer CAN do

* take a natural-language request from an operator or an LLM,
* select a fixture (or, in a future phase, return an LLM-derived
  structured proposal),
* sanitize the proposal against a closed list of forbidden phrases,
* forward sanitized text to the Phase 14A mission compiler,
* render an audit bundle that records exactly what happened.

## 3. What the proposal layer MUST NOT do

The following are blocked at the package, sanitizer, CLI, and test
levels:

| Forbidden                                              | Enforcement                                              |
|--------------------------------------------------------|----------------------------------------------------------|
| publish to `/cmd_vel`, `/cmd_vel_authorized`           | nothing in the package imports a ROS publisher           |
| toggle the safety supervisor                           | no API into supervisor state from this layer             |
| override e-stop                                        | sanitizer rejects matching text                          |
| disable lidar / continue despite sensor failure        | sanitizer rejects matching text                          |
| run shell, run code, run network commands              | sanitizer rejects matching text                          |
| invoke a remote LLM API                                | no LLM SDK imports in the package; test asserts this     |
| invent waypoints / coordinates                         | Phase 14A compiler does not invent waypoints (REQ-MCOMP) |
| bypass the compiler                                    | adapter only invokes the compiler on sanitized text      |
| fabricate runtime execution                            | proposals never produce live runtime evidence            |

If a future change wants to relax any of these, it must:

1. produce a Phase ADR,
2. update `docs/HUMAN_TO_AUTONOMY_BOUNDARY.md` and
   `docs/LLM_MISSION_PROPOSAL_LAYER.md`,
3. add a requirement with an explicit test that demonstrates the
   safety supervisor remains authoritative.

## 4. Why these boundaries

LLMs are useful for *translation* and *planning*, not for
*authority*. They are stochastic, sensitive to phrasing, and
trained on data that knows nothing about this robot's safety
state. The proposal layer therefore treats every provider output
as untrusted input. The sanitizer is the first filter; the
deterministic Phase 14A compiler is the second; the runtime
safety supervisor remains the only path to motion.

## 5. Audit trail

Every proposal that passes through the pipeline produces an audit
bundle (see `docs/MISSION_PROPOSAL_AUDIT.md`). The bundle records
the provider mode, the sanitizer result with diagnostics, the
sanitized text sent to the compiler, the compiler status, and the
verbatim safety-boundary disclaimer. The bundle is read-only; the
proposal layer never mutates a previous bundle on a new run.

## 6. Honesty rules

* No artifact in `mission-proposals/` represents a runtime mission.
* No artifact in `mission-proposals/` claims safety certification.
* No artifact in `mission-proposals/` is generated by a real LLM
  call.
* A proposal that compiles cleanly is *eligible* for review by an
  operator; it is not authorised to run on the robot.

If a future external provider is added and an audit bundle is
produced from a real LLM call, the bundle must record the provider
endpoint, the provider model, and the request ID in
`raw_response`. The sanitizer rules still apply, and the audit must
state explicitly that the proposal originated from an external
provider.
